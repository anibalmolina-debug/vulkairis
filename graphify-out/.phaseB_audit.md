## 3. Gaps (ordered by severity)

1. **Driver path bypasses the union model.** `VulkanModProgramBridge.link()` calls
   per-stage `ShaderTranslator.preprocessGlsl` + `buildUnifiedBindingMap` (private
   duplicate) and never calls `ProgramTranslator.translate` / `UnifiedTranslationService`.
   Consequences: per-stage uniform blocks can differ across stages (vertex has
   `projection`, fragment has `rainStrength`) while sharing dense binding 0 — descriptor
   mismatch risk the union model was built to prevent. The golden fixtures therefore
   prove a path the driver does not currently execute.
2. **Varying split is helpers-only, never applied.** `splitVarying` /
   `splitStructVarying` / `assignDenseLocations` have zero call sites. Slot accounting
   (`nextLocation += slots` in both bridge and `ProgramTranslator`) avoids overlap but
   no declaration is ever scalarized — a `mat4`/`struct`/array varying keeps one
   declaration while consuming N slots. Rank==location discipline is accounting, not rewrite.
3. **Legacy `vulkairis_*` inputs can never satisfy the vertex-format table.**
   `ftransform`/`gl_Vertex` packs gain `in vec4 vulkairis_Vertex;` (etc.), which enters
   `requiredInputs`; no `DefaultVertexFormat` contains those names, so `chooseVertexFormat`
   succeeds but the uncovered-input check fails the link. Every fixed-function-vertex pack
   is a guaranteed `failLink` on the bridge path. Needs either format-table entries or
   rewriting legacy attribs onto real attributes (`Position`, …).
4. **`shadow2DProjLod` missing from `mappedCallee`.** `shadow2D`, `shadow2DLod`,
   `shadow2DProj` are wrapped; the fourth GLSL-120 builtin `shadow2DProjLod` is not and
   would reach Shaderc undeclared. (No `shadow2DBias` builtin exists — correctly absent.)
5. **No precision-strip / non-const-`const` demotion.** Pack `precision mediump float;`
   lines are preserved (plus `highp` lines added); `LegacyKeywordPass` handles only
   `attribute`/`varying`. A `const` with non-constant initializer is left for Shaderc
   to reject. Plan §4.3 lists both; neither exists (verified: no `demote`/precision-strip
   code in `translation/`).
6. **No reversed-Z handling in translation.** Only mention is `core/RenderMatrices`
   javadoc; no depth-range rewrite verified against VulkanMod depth. Falls under §4.3
   "reversed-Z handling matching VulkanMod depth" — unimplemented.
7. **No fullscreen/entity/sky vertex roots.** No special-casing in `translation/` for
   procedural fullscreen passes (cf. `testpack/ShaderTestPacks.fullscreenVertex` fixtures
   exist only as harness fixtures, never translated in a golden test).
8. **`bool` varyings unhandled.** `bool→int` is block-scoped only; a `bool` varying or
   `bool` function signature interacting with the block is untouched (signatures
   intentionally so; varyings are a hole).
9. **`gl_Fog` is flag-only.** `needsFog` injects `VulkairisFogParams` + block member, but
   values are Phase E work (bridge documents "values not yet transported") — correctly
   staged, noted for E.
10. **Deliberately unmapped (compiler-reported by design):** `gl_Fog` beyond the struct,
    `gl_LightSource`, inverse matrices (`gl_ModelViewMatrixInverse`, …). Acceptable per
    code docs, but inverse matrices are common in BSL-family packs — expect fixture
    failures there.

## 4. Vertex-format table coverage

12 candidates, smallest-first (`POSITION` → `NEW_ENTITY`); compositions verified against
1.21.1 Blaze3D in comments. Covers `Position/Color/UV0/UV1/UV2/Normal` combos only.
Uncovered by design (fail link with reason): `UV1`-only inputs outside `NEW_ENTITY`
shape, any tangent/`MidTexCoord`-class extras (Phase D `TerrainVertexContract` work),
and — per gap §3.3 — all `vulkairis_*` legacy attribs.

## 6. Contract note (no action taken)

Dense-binding ordering is implemented twice with identical semantics
(`ShaderTranslator.collectDescriptorNames` + bridge `buildUnifiedBindingMap`, both
"injected block first, then first-seen vertex→fragment"). §4.2 asks to formalize this
as a shared contract — recommend extracting one shared helper when §3.1 is fixed, since
that edit touches the same code.
