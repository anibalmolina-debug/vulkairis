Executive SummaryVulkairis should not begin by adding more shader effects. Its first priority is proving that a shader pack can pass through every stage of a real rendering pipeline and visibly affect the Minecraft world. A pack may be found and its shader files may compile while the world remains unchanged if render passes are gated off, scene geometry is not routed through the programs, resources are bound incorrectly, or the final output never reaches presentation.The three highest-priority blockers are:Render passes that are disabled, gated, or not connected to the actual renderer.Incomplete shader-to-GPU integration: render targets, resource bindings, geometry routing, and GPU execution.An incomplete end-to-end chain from shader-pack parsing through final frame output.SUCCESS DEFINITIONA supported test pack is detected, parsed, compiled, and executed; its shader changes are visible in-world; terrain and the player view render correctly; failures identify the exact stage and reason; and the normal renderer remains usable when a pack is unsupported.2. Scope, assumptions, and rulesTarget Minecraft/Fabric version: 1.21.1. Architecture and end-to-end data flowThe intended pipeline should be explicit, observable, and testable:Discover installed shader packs and read the selected pack archive/directory.Parse pack metadata, shader programs, settings, includes, uniforms, samplers, and pass dependencies.Rewrite supported legacy GLSL conventions and resolve includes/macros.Compile translated shaders to the backend-compatible representation, including SPIR-V where required.Build a render plan: passes, dependencies, targets, textures, samplers, and resource lifetimes.Create GPU programs and resources; bind Minecraft state and pack-defined inputs.Route actual Minecraft geometry and scene data through the appropriate passes.Execute shadow, geometry, composite, and final passes in dependency order.Present the final image, report diagnostics, and preserve fallback behavior.Add structured stage logging so every pack load can answer: which stage ran, what it produced, and why it failed. Do not rely on a single generic 'shader failed' message.4. Phase 2 â€” Complete shader-pack parsing and GLSL translation6.1 Pack discovery and parsingSupport the intended pack container format, including ZIP-based packs and directory packs if required by the product scope.Parse pack properties/settings and discover shader stages, program names, includes, and declared resources.Resolve include paths consistently; detect missing files and include cycles with clear diagnostics.Parse pass dependencies and identify unsupported directives before GPU setup.Make pack reload atomic: build a new pack state separately and swap it in only after validation succeeds.6.2 GLSL rewritingDefine a documented set of supported OptiFine/Iris conventions for the initial compatibility target.Implement deterministic rewriting for supported legacy syntax, macros, version directives, and compatibility aliases.Resolve #include and conditional compilation in the correct order; preserve useful source locations for diagnostics.Reconcile vertex/fragment interface declarations and ensure generated bindings follow the Vulkan backend's rules.Do not silently strip unknown directives. Emit a precise unsupported-feature warning or fail the pack with a reason.6.3 Compilation and SPIR-V validationUse the compiler/toolchain supported by the Minecraft 1.21.1 target and the selected Vulkan path.Validate generated source before compilation and validate compiled modules before program creation.Capture compiler messages, source file, line/column, stage, and generated-source mapping.Cache compilation results using a key that includes pack content, transformation version, target version, and relevant options.Test vertex and fragment stages independently, then validate linked interfaces and pipeline creation.Exit criteriaThe test pack parses and compiles without unexplained warnings or errors.A deliberately invalid shader produces an actionable error and does not crash the game.Reloading the pack replaces the old pack state without leaking or mixing resources.7. Phase 3 â€” Render plan, render targets, and G-buffer7.1 Render-plan builderCreate a plan representation for passes, dependencies, inputs, outputs, and required state.Validate the dependency graph for missing inputs, cycles, invalid pass references, and unsupported stage combinations.Topologically order passes where dependencies allow it and preserve pack-defined ordering where required.Track pass capability requirements and provide explicit reasons when a pass cannot run.Keep plan construction separate from GPU execution so it can be unit-tested without rendering a world.7.2 Render targets and attachmentsAllocate color and depth targets with formats supported by the target GPU/backend.Implement multiple render targets where the pack requires them.Define clear/load/store behavior, sample counts, and attachment compatibility per pass.Implement resize handling and recreate targets when the window, render scale, or relevant pack settings change.Implement required copies, blits, mipmap generation, and depth transfers explicitly; do not assume an OpenGL operation maps one-to-one to Vulkan.7.3 G-buffer dataDetermine the actual per-pack data contract for color, depth, normals, material data, and any additional outputs.Ensure geometry shaders write the expected outputs and later passes sample the matching targets.Validate formats, precision, coordinate conventions, and depth conventions across passes.Add debug views for individual attachments so blank, inverted, or misaligned data is easy to identify.Exit criteriaA validated render plan can be printed and inspected before execution.All required targets exist with compatible formats and dimensions.Debug views confirm that scene color and depth contain valid world data.8. Phase 4 â€” GPU resources, descriptors, uniforms, and synchronization8.1 Resource bindingBuild a typed resource table for uniform buffers, storage buffers, sampled textures, samplers, and other supported inputs.Map shader declarations to backend binding locations consistently and validate collisions or missing resources.Create a uniform provider for Minecraft state such as camera matrices, camera position, world time, weather, and other supported pack-defined values.Support pack-defined uniforms and samplers where the compatibility specification requires them.Supply documented defaults only when valid; otherwise report missing required data rather than silently binding an unrelated resource.8.2 GPU lifecycle and synchronizationTrack ownership and lifetime of programs, buffers, textures, views, samplers, and descriptor resources.Destroy resources only when no in-flight GPU work can reference them.Implement correct command ordering and synchronization between geometry, shadow, composite, and final work.Handle reload, resize, dimension switch, device/backend failure, and shutdown without stale handles.Add validation-layer runs and leak checks to the development test process.Exit criteriaRequired resources are bound to the intended shader inputs, with validation errors treated as test failures.Repeated reloads and resize cycles do not cause stale resources, crashes, or persistent GPU errors.9. Final recommendationThe fastest credible route to a working Vulkairis prototype is to stop expanding the feature list and prove one complete render path. First identify and repair the disabled/incomplete pass gates; then load, transform, compile, bind, execute, and present a minimal shader on real terrain. Only after that succeeds should the work expand to the complete G-buffer, geometry families, shadows, composite effects, compatibility, and optimization.NON-NEGOTIABLE MILESTONEDo not call shader loading complete until a shader program is proven to execute on real Minecraft scene data and its output is visible in the final frame.
